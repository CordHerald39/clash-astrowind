流媒体出现不能播放、地区提示、空白播放器或加载失败时，不要先改节点或整表重写规则。应先把错误页面所对应的那次请求，写成官方路由规则能够识别的字段。规则只按从上到下的顺序匹配域名、IP、进程等条件；错误文案本身不会自动变成配置。记下的内容，是后续写 `DOMAIN`、`GEOSITE`、`GEOIP` 或 `PROCESS-NAME` 的依据，而不是对播放结果的承诺。

## 适用条件

同时满足以下情况时，应先记录再改规则：播放器或网页已打开并能看到失败提示；出站握手或节点检测看起来可用，但内容仍失败；尚未确定该请求走了 `DIRECT`、某代理还是 `REJECT`；准备改 `GEOSITE`、`DOMAIN-SUFFIX` 或表尾 `MATCH` 之前。

若流量根本未进入规则列表，记录错误页也对应不到 `rules`。判断依据是：你至少能写出失败时的目标主机名，或失败进程名/包名，才有条件对照规则类型。

## 按错误页对齐规则字段

一次失败记一份，避免把广告主机和媒体主机混在同一条。

1. 记完整主机名。`DOMAIN` 匹配完整域名；`DOMAIN-SUFFIX` 匹配后缀。文档说明：`google.com` 能匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。流媒体 CDN 经常是另一套后缀，只记站点首页会导致后续规则碰不到真正拉流的主机。
2. 记准备用的模糊匹配种类。`DOMAIN-KEYWORD` 是关键字；`DOMAIN-WILDCARD` 仅支持 `*` 与 `?`，且与配置文件其他地方的 Clash 格式通配符不相同；`DOMAIN-REGEX` 才是正则。主机名每次都变时，必须标明将用哪一种，不能只写「都能对上」。
3. 记是否打算用 `GEOSITE`。它匹配 Geosite 内域名，部分内容参考 v2fly/domain-list-community。类别名不是播放器产品名。判断依据是：你记下的主机是否真能被该类别覆盖。
4. 记解析后的 IP 与地理字段。`IP-CIDR`、`IP-CIDR6`、`IP-SUFFIX`、`IP-ASN`、`GEOIP` 都作用在目标 IP。附加参数 `no-resolve` 会在匹配目标 IP 类规则时跳过 DNS 解析；若更早的匹配已经触发过解析，带 `no-resolve` 的 IP 规则仍可能命中。记录时写清当时手里是域名还是 IP、是否允许解析，避免「页面上是域名、规则却按未解析 IP 来写」。
5. 记进程、包名与入站。桌面可用 `PROCESS-NAME`、`PROCESS-PATH` 及对应 WILDCARD/REGEX；Android 上 `PROCESS-NAME` 可以匹配包名。同时记下 `DST-PORT`、`SRC-PORT`、`IN-PORT`、`IN-TYPE`。浏览器内嵌播放与独立客户端进程不同，错误页看起来可以一样，匹配条件不同。
6. 记表位置与逻辑组合。规则顶部优先于底部；`MATCH` 匹配所有请求且无需条件。`AND`、`OR`、`NOT` 必须注意括号；`SUB-RULE` 会进入子规则；`RULE-SET` 引用规则集合。应写「这次失败从上往下会先碰到哪一类规则、出站是什么」，而不是只抄错误文案。
7. 记 `NETWORK` 是 tcp 还是 udp。若请求为 udp 而节点没有 udp 支持，会继续向下匹配。直播或 QUIC 失败应标明协议，以免误判成域名规则写错。

每条记录至少包含：时间、完整域名、是否已有 IP、进程或包名、端口、tcp/udp、当前配置里可能命中的第一条规则类型、该规则出站、表尾 `MATCH` 指向何处。图片不能替代这些字段，规则引擎看不到页面截图。

## 记录对不上时的下一步

只有文案没有主机名：先补目标主机，不要用猜测的 `DOMAIN-KEYWORD` 直接上线。只有 IP 没有域名：按 `IP-CIDR` 或 `GEOIP` 记录，并标明是否加 `no-resolve`；不要把 IP 国家代码写成账号地区。主机名每次变化：改记后缀、正则或 GEOSITE 类别，并写明通配符限制。记下的精确规则永远排在过宽关键字或 `MATCH` 之后：下一步是调整顺序。逻辑规则括号不清：先拆成单条 `DOMAIN` 再组合。完成本文记录后，再改流媒体相关规则。
