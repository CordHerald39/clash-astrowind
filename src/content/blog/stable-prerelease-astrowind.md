电脑端 Clash Verge Rev 在 GitHub 同时提供正式发布与滚动构建。选错通道，常见情况是日常使用撞上未修复缺陷，或本应验证新改动却装到已废弃标签。下文只依据项目说明，说明适用条件、判断依据，以及失败后的下一步。

## 先分清三类发行通道

项目文档用表格回答“应当怎样选择发行版”。Stable 是正式版，特征为高可靠性，适合日常使用，下载入口是 Release 页面。Alpha 被标明为废弃，用途是测试发布流程。AutoBuild 是滚动更新版，适合测试反馈，并写明可能存在缺陷。

因此，稳定版对应 Release 上带版本号的安装包；预发布或测试通道应理解为 AutoBuild，而不是 Alpha。把 Alpha 当成“更新的测试版”不符合官方定义。

近期正式标签包括 v2.5.7、v2.5.6、v2.5.5，每条都附修复说明和分平台下载链接，属于按版本冻结的正式包，与 autobuild 标签下的滚动包不是同一通道。

## 稳定版的适用条件与下载判断

同时满足这些条件时选 Stable：把软件当作日常工具使用；不能接受内核启动失败、服务模式或 TUN 不可用、系统代理状态错乱；没有精力跟踪滚动构建并随时回退。官方安装说明要求到发布页下载对应安装包，支持 Windows（x64/x86）、Linux（x64/arm64）和 macOS 11+（Intel 与 Apple）。Windows 安装说明写明不再支持 Win7，系统版本不满足时更换发行通道无效。

在 Release 页判断安装包：先确认标签是以 v 开头的版本号，再按操作系统和 CPU 架构选文件。Windows 提供“正常版本(推荐)”与“内置 WebView2 版”；后者体积较大，仅在企业版系统或无法安装 WebView2 时使用。macOS 按 Apple M 芯片或 Intel 芯片区分。Linux 按 Debian 系 deb 或 Redhat 系 rpm 选择，并匹配 64 位、ARM64 或 ARMv7。这些只解决运行环境匹配，不能替代“正式版还是滚动版”的判断。

## 滚动预发布只在测试场景使用

仅当你的目标是验证尚未进入正式版的改动、并能提交测试反馈时，才使用 AutoBuild。官方已提示该通道可能存在缺陷。若机器承担必须保持可用的任务，即使滚动包日期更新，也不符合适用条件。

不要使用 Alpha：它已废弃，且定位是测试发布流程，不能当成“比稳定版新、又比 AutoBuild 稳”的中间路线。

## 失败时如何回退与排查

若已安装 AutoBuild 后出现无法启动、服务装不上、代理或 TUN 异常，下一步是返回 Release 页，安装当前带版本号的正式包，而不是继续拉取更新的滚动构建。正式版说明多次覆盖 Windows 服务权限误判、安装服务失败、macOS 内核偶发启动失败、服务被强制结束导致日志丢失等，应在正式通道内按该版本说明和项目文档处理。

升级正式版后若提示服务版本或协议不兼容，按说明重新安装服务，而不是改下测试通道。Windows 在服务安全检查未通过时，较新正式版会说明原因并提供修复文档链接，应先跟随该说明。架构选错或缺少 WebView2 时，更换对应安装包即可，不必改变发行通道。系统仍为 Win7 时，官方已不再提供支持，需更换受支持的系统后再安装稳定版。

若回退到稳定版后仍失败，查阅项目文档页与发布说明中的常见问题入口，核对服务残留、目录权限和安装包架构，避免在 Alpha 与 AutoBuild 之间反复换包。
